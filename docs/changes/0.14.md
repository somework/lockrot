# Upgrading to 0.14

lockrot 0.14 grades each finding from its flags, writes report-2 and reads baseline-2 only. A
committed baseline file from 0.13 makes every check run exit `2` until you regenerate it with
`--generate-baseline` ([Baselines](#baselines)). Find your install in
[How 0.14 reaches you](#how-014-reaches-you).

## What changes on the first run {#what-changes}

- **The verdict is the grade.** The flags add up to a score, the score's band is the verdict, and
  the cause word moves to `lead` ([The score](../verdicts.md#score), [Flags](../verdicts.md#flags)).

- **Advisories score.** A counted advisory flags the package `vulnerable` and adds to its score, so
  a grade value of `--fail-on` can fail on it
  ([Security advisories](../verdicts.md#security-advisories)).

- **More packages are asked about advisories.** lockrot sends the name of every package that the
  run checks, vcs and path packages included. With `extra.lockrot.advisory-lookup:
  composer-repositories`, it sends only the names of the packages from a Composer repository
  ([Which advisories count](../verdicts.md#which-advisories-count)). The move check also loads the
  packages that a solve needs and the run did not read. While advisory blocking is on, it asks for
  their advisories
  ([What lockrot contacts](https://github.com/somework/lockrot/blob/v0.14.0/SECURITY.md#what-lockrot-does-and-does-not-do)).

- **An `ignore` entry does not hide advisories.** It accepts the package's maintenance flags only
  ([Accepting advisories](../verdicts.md#accepting-advisories)).

- **A PHP cap is a flag.** A package whose installed `require.php` stops below the newest PHP that
  the project allows is `capped` ([Capped](../verdicts.md#capped)). `--fail-on=capped` and every
  grade value can fail on it, because its 8 points can lift a score to `high` or `critical`.
  `--fail-on=stale` does not.

- **Composer's abandoned ignore list counts.** A package on it raises no S1
  ([Composer's abandoned ignore list](../verdicts.md#abandoned)).

- **`--fail-on=unchecked` fails on more gaps.** An `accept-unchecked` entry accepts a gap that no
  rerun closes ([What `--fail-on=unchecked` fails on](../ci.md#what-unchecked-fails-on)).

- **A refused Composer variable stops the run.** On Composer 2.10 and later, a value that Composer
  refuses in a blocking or policy variable (`COMPOSER_NO_BLOCKING=yes`) or in `config.policy`
  exits `2`, `--offline` too ([The move check](../verdicts.md#the-move-check)).

- **The documents are new.** report-2, explain-2, baseline-2 and config-2
  ([JSON schemas](../schema.md)).

Each run that has a gate, or writes `json`, `sarif`, `gitlab` or a baseline, prints a one-line
upgrade notice on stderr. Keep stderr out of a report file: do not add `2>&1` to a command whose
stdout is the report.

## Baselines

lockrot 0.14 refuses a baseline-1 file with exit `2`, and no option skips the default
`lockrot-baseline.json`. `--explain` does not read the baseline. Review the findings first, then
write a baseline-2 file.

- **On the command line, with the plugin or the PHAR:** run the commands of
  [Moving from a baseline-1 file](../baseline.md#moving-from-a-baseline-1-file).

- **On `somework/lockrot-action`:** you cannot commit from the job, so the step writes the file and
  you commit it.

    1. Move the file aside, and push. If the `baseline` input of the job or the
       `extra.lockrot.baseline` key of `composer.json` names the file, move the file at that path.
       Remove the input and the key in the same commit: a run without the file that they name
       exits `2` with `lockrot: <path> not found`.

        ```bash
        git mv lockrot-baseline.json lockrot-baseline.0.13.json
        git commit -m "chore: move the 0.13 lockrot baseline aside"
        git push
        ```

    2. Read the findings of the next run. Then run the job once with `generate-baseline: true`, and
       upload the file that it writes. Put back the input or the key that you removed in the same
       commit, because a run without the file that they name exits `2`.

        The file is at the path that they name, else at `lockrot-baseline.json`, in the directory
        that the `working-directory` input of the action names. Set that path in the `path` of the
        upload step. The upload step reads `path` from the checkout root, so put that directory
        first, such as `app/lockrot-baseline.json`:

        ```yaml
        - uses: somework/lockrot-action@v1
          with:
            target-php: '8.4'
            generate-baseline: true
        - uses: actions/upload-artifact@v7
          with:
            name: lockrot-baseline
            path: lockrot-baseline.json
        ```

    3. Download the artifact, then commit the new file and delete the old one:

        ```bash
        git add lockrot-baseline.json
        git rm lockrot-baseline.0.13.json
        git commit -m "chore: regenerate the lockrot baseline as baseline-2"
        ```

    4. Remove `generate-baseline: true` from the job.

    You can also run step 2 on your machine with the plugin or the PHAR, and use the same
    `--target-php` as the job.

## Scripts that read the report {#scripts}

A `jq` query on a cause word in `.verdict`, or on `.counts.<cause>`, matches nothing in report-2.
[Migrating from report-1](../schema.md#migrating-from-report-1) gives the field that replaces each
one and a guard on the document's `$schema`. The same applies to the report that the `html` page
embeds, and to a check that validates against `report-1.json`.

A check that validates against a schema file of the installed package or the PHAR needs the file's
number: `resources/lockrot-report.schema.json` is `resources/lockrot-report-1.schema.json`, and the
report-2 schema is `resources/lockrot-report-2.schema.json`. The same holds for `explain`,
`baseline` and `config`.

## How 0.14 reaches you

| Install | Moves to 0.14 | To take 0.14 | To stay on 0.13 |
|---|---|---|---|
| The PHAR with `self-update` | At the next `self-update` | Regenerate the baseline | [Stay on 0.13 with the PHAR](#stay-on-013-with-the-phar) |
| The PHAR at a pinned `LOCKROT_VERSION` | Never | Set `LOCKROT_VERSION=v0.14.0`, and regenerate the baseline | Change nothing |
| The Composer plugin | Never: a `^0.13` requirement stops at 0.13.x | [The plugin](#the-plugin) | Change nothing |
| `somework/lockrot-action@v1` | From v1.2.0 of the action. With `version: latest`, from the lockrot release | Regenerate the baseline ([Baselines](#baselines)) | Set `version: 0.13.0` |
| The Docker image | `latest` moves with v1.2.0 of the action | Use the `0.14` tag, and regenerate the baseline | Use the `0.13.0` tag |
| PHIVE | Never: `phive update` stays on 0.13.x | Run `phive install somework/lockrot@^0.14`, and regenerate the baseline | Change nothing |

!!! warning
    If a job runs `somework/lockrot-action` before v1.2.0 with `version: latest`, upgrade the action
    to v1.2.0, or set `version: 0.13.0`. Before v1.2.0, the action writes the job summary from a
    second run with `--offline`. On 0.14, that summary shows no advisory, and its gate line can
    differ from the result of the step.

### Stay on 0.13 with the PHAR

`self-update` on a 0.13 archive installs 0.14 at once, with no option and no prompt
([Which release it installs](../phar.md#which-release-it-installs)). `self-update` cannot pin a
release or go back. To stay on 0.13, or to go back to it after the move:

1. Stop calling `self-update` in the job.
2. Download the 0.13.0 release, with its checksum and signature:

    ```bash
    set -e
    LOCKROT_VERSION=v0.13.0
    curl -fsSL -O https://github.com/somework/lockrot/releases/download/$LOCKROT_VERSION/lockrot.phar
    curl -fsSL -O https://github.com/somework/lockrot/releases/download/$LOCKROT_VERSION/lockrot.phar.sha256
    curl -fsSL -O https://github.com/somework/lockrot/releases/download/$LOCKROT_VERSION/lockrot.phar.asc
    sha256sum -c lockrot.phar.sha256
    ```

3. Verify the signature with `gpg --verify lockrot.phar.asc lockrot.phar`, or the build
   provenance with `gh attestation verify lockrot.phar --repo somework/lockrot`
   ([Verifying the download](../phar.md#verifying-the-download)).
4. Put the file in place of the 0.14 archive.
5. If you committed a baseline-2 file, restore the baseline-1 file from your history. Do this
   before the first 0.13 run. Else delete the file, and run `--generate-baseline` on 0.13. lockrot
   0.13 exits `2` on a baseline-2 file on every run, `--generate-baseline` included
   ([What 0.13 does with 0.14 files](../phar.md#which-release-it-installs)). Also remove the config-2
   values that [Machines on 0.13](#machines-on-013) lists.

### The plugin

1. Require the new minor, and commit `composer.json` and `composer.lock`:

    ```bash
    composer require --dev somework/lockrot:^0.14
    ```

2. Regenerate the baseline ([Baselines](#baselines)), with the project's `--target-php`.

On Composer older than 2.4, the plugin cannot check advisories on any run (S10 reason
`composer_too_old`), and `accept-unchecked` cannot accept that reason. So `--fail-on=unchecked`
fails every run. Upgrade Composer, or run the PHAR, which bundles a newer Composer.

With `install-time-strict` and `fail-on: unchecked`, an advisory gap stops the install, where 0.13
let it through ([`install-time-strict`](../install-time.md#install-time-strict)):

- On Composer 2.2 and 2.3, every `composer require`, `update` or `install` that changes a package
  stops.
- A repository without an advisory feed (`no_feed`), a failed advisory lookup (`lookup_failed`) or
  an exhausted [budget](../install-time.md#time-budget) stops the install. A cold-cache CI install
  can run out of budget.

Before you upgrade such a project, remove `unchecked` from the `fail-on` that installs read, or
accept a `no_feed` gap with [`accept-unchecked`](../configuration.md#accept-unchecked).

When nothing is graded and the gate fails, the install-time block prints its short form with the
`gate:` line ([Never silent](../install-time.md#never-silent-about-a-package-it-could-not-check)).

## Machines on 0.13

lockrot 0.13 cannot read a baseline-2 file or some keys of config-2
([What 0.13 does with 0.14 files](../phar.md#which-release-it-installs)). Upgrade every machine
and CI job that shares the project before you commit a baseline-2 file, a `fail-on` list, a
`capped`, `vulnerable` or `vulnerable-*` value, an `ignore` entry with `flags`, `accept-unchecked`
or `advisory-lookup`.

A page that `--format=html` wrote with 0.13 keeps opening as it did: each page embeds its own
renderer and its own report. The page of lockrot 0.14 reads report-2 only. To view a report-1
document, rerun lockrot 0.14, or open the document with
[lockrot-report](https://github.com/somework/lockrot-report) 0.13.
